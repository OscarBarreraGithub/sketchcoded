# Vision, implementation, guide and checklist review

Reviewed 2026-09-28, then implemented with the user’s authorization. See “Implemented follow-up” below for current status; the findings preserve the initial review.

The original screenshot-flow workflow is substantially implemented. The main work now is protecting edits, finishing the zoom behavior, correcting gaps in the checker and public demo, and reconciling the records. The interactive tutorial is the clearest explicitly requested feature still waiting. The later LLM generation/review workflow remains deliberately deferred.

This review compares the original brief, dated requests and decisions, current checklist, functionality catalogue, Sketchcoded board, code, tests, public guide and deployed demo. It distinguishes an undrawn page in the example board from an unimplemented app feature. No user board or product code was changed.

## Fix first: confirmed behavior

### R1 — Returning to the boards page can discard the last edit

**High priority; reproduced in an isolated browser with temporary data.** Edit a screen purpose, close its editor, and immediately click the Sketchcoded brand to return to the boards page. The stored purpose remains the old one.

The brand calls `onHome` directly ([App.tsx](../src/App.tsx#L532)). Autosave waits 650ms, and unmounting cancels that timer ([useProject.ts](../src/useProject.ts#L119), [cleanup](../src/useProject.ts#L196)). The board switcher already waits for `flush()`, but this route does not. Internal navigation does not trigger the browser's `beforeunload` warning. Browser history changes also lack a save guard in the route handler; that adjacent path was inspected, not separately reproduced.

**Recommendation:** save before every route that leaves a board; keep the board open if saving fails. Test an edit followed immediately by Home and browser Back. This is more urgent than adding features.

### R2 — An agent refresh can overwrite typing that started during its request

**High priority; reproduced with a controlled network delay on temporary data.** Let an external API update start the browser's refresh, hold the project GET response, type in the purpose field, then release the response before autosave starts. The new typing disappears from both the interface and the eventual saved copy.

The refresh checks whether the project is dirty before awaiting the GET, then applies the result using that earlier decision. It does not recheck the local version after the request ([useProject.ts](../src/useProject.ts#L165)). It also clears undo history when applying the refresh.

**Recommendation:** capture the local edit version and revalidate it when the response arrives. Preserve newly started edits and use the existing conflict path when necessary. The current test only covers an idle board receiving an agent update.

### R3 — High browser zoom still leaves too little workspace

**High priority; measured using real Chromium tab zoom at both laptop sizes in the checklist.** The document correctly stays within the window, but the header and toolbar consume almost all of the available height. No page overflow does not imply a usable board.

| 1440×900      | 125%         |                              495.2 |
| 1440×900      | 150%         |                              394.7 |
| 1440×900      | 200%         |                              192.0 |

At the final size, the board is only about 57 physical pixels tall. The floating controls occupy more space than the board. [Measured screenshot](screenshots/review-2026-09-28-zoom-1280.png).

**Recommendation:** compact or consolidate the chrome further at short effective heights, while retaining reachable controls. Add a workspace-usability assertion, not just document-overflow assertions. Existing native zoom tests use a taller 1440×1000 window and do not cover every view at both required laptop sizes.

### R4 — AI pages can pass review despite being unreachable or having no exit

**Medium priority; reproduced in memory.** Two undrawn `leftToAi` screens, one an entry and the other disconnected, return no findings even when neither has a way onward.

The [unreachable](../shared/graph.ts#L254) and [dead-end](../shared/graph.ts#L274) conditions skip all planned frames. The [one-way check](../shared/graph.ts#L513) correctly distinguishes ordinary planned frames from AI pages. The documentation says an AI page is specification and should be checked like a drawn page.

**Recommendation:** use the same distinction for all applicable navigation checks and cover disconnected AI pages and AI pages without exits.

### R5 — Short codes can be reused after deletion

**Medium priority; reproduced in memory.** Create P1 and P2, delete P2, then add a frame: the new frame becomes P2. The allocator reads the maximum among surviving records ([model.ts](../shared/model.ts#L229)). The same allocation approach handles sketches and ideas. The existing test deletes a middle item while a higher code survives, so it misses this case.

This violates the promise that a code continues to mean the same thing throughout the life of a board, which matters for pasted agent prompts and old conversations.

**Recommendation:** retain a per-category high-water mark or equivalent durable allocation history. Keep the F-to-P migration, which works as intended.

### R6 — The public demo does not preserve several app behaviors

**Medium priority; present-data failures confirmed on the deployed site.**

- Home's GitHub pin is a valid link pin, but clicking it says “GitHub has no path tied to it yet.” The public player checks only yarn and never handles link pins ([demo.js](../../sketchcoded-site/demo.js#L447)). It should at least identify the URL as the app does, with an explicit link if appropriate.
- Guide has `leftToAi: true`, but the public player says it needs a drawing. If retaining a drawings-only public player is intentional, it should explain the flag accurately. Whether to render standard pages there is a scope choice; showing every AI frame as missing work is misleading.
- Shift-scroll can pan every frame completely out of sight. A large pan left **zero visible frames**. `apply()` and the pan handlers have no content clamp ([demo.js](../../sketchcoded-site/demo.js#L201)), despite the general canvas rule.
- Player pin targets measure **34×34px** on desktop and at a 390px mobile viewport; the checklist requires at least 44×44px ([demo.css](../../sketchcoded-site/demo.css#L428)).

Code inspection also shows that the public player treats Dismiss like one Back step and its Step back control uses app history rather than independent test snapshots. Those differences are not exercised by the current eight-thread board, so they are compatibility gaps for future exports rather than observed failures of today's route set. Detail pins and mobile drawings likewise have no dedicated player path.

**Recommendation:** keep the public board read-only, preserve the user's drawings, and make its supported navigation agree with the application. Do not add the workstation's editing panels to the public demo.

### R7 — The checker treats static annotations as missing navigation

**Product-model gap; confirmed on the user's board, recommendation needs design judgment.** The current Sketchcoded board has 22 `unconnected-pin` findings. Some are legitimate missing routes, but examples such as “Title and tagline,” “Runs local, sketches never leave,” “Project name,” and “No overlap, lots of space” describe content or layout rather than a trip to another screen.

The schema supports interaction, detail and link pins only. Every ordinary pin without yarn gets told to add navigation ([graph.ts](../shared/graph.ts#L368)). Reasoned acceptance can silence an individual warning, but repeated acceptances are an awkward substitute for representing this intent.

**Recommendation:** consider a content/annotation or local-action intent that does not require yarn. Keep these authored notes; do not delete them or invent destinations to make review green. This is a recommended refinement, not an explicit original request for a new pin kind.

## Records that could misdirect the next agent

The most consequential documentation issue is that the board, which agents are told is canonical, retains superseded instructions. Its generated `planningOutline()` repeats them in handoffs and exports.

- **I12** still asks for dashed planned threads on the board, although the user explicitly removed them.
- **I36** and its placed pin still say web and mobile are side by side and ask the user to decide, although the toggle was implemented. The Screen editor purpose repeats the old layout.
- **I18** still says clicking a card opens it; single click now selects its threads, while the tape, arrow and double-click open it.
- **I6** retains the old used/unused filter description; the current library has New/Used sections.
- The 97-idea snapshot has no entry describing the later Threads category filter or short codes, despite both appearing in the functionality catalogue.
- **I69/I70** still contain repository-publication and projects-page placeholders. The repository is public; the projects destination has no distinct page.

The README additionally retains F-code examples, page-scrolling instructions, side-by-side drawings, a requirement for a drawing before adding pins, and a first-launch claim that no longer matches the boards landing page. `docs/GRAPH.md` still says planned frames cannot have pins and lists only four colors. `docs/FUNCTIONALITY.md` repeats older planned-card and editor descriptions. The top of PROGRESS and USABILITY_PASS describe historical states; their dates should remain, with a clear pointer to current status instead of being presented as the latest acceptance report.

**Recommendation:** reconcile active specifications with the dated decisions, explicitly marking old requests superseded. Preserve the original brief and historical record. Do not silently rewrite the user's pin wording during a review-only task.

Also clarify status vocabulary: **placed as a pin is not implemented in code**. Unplaced ideas include already-built features. The plan currently tracks drawing/placement work, so it cannot by itself answer how much software remains to build. A guide explanation is needed; a separate implementation-status field would be a new product decision.

## Checklist: what belongs elsewhere

**Yes: the entire “How to read a board” section is tool-specific workflow, not a general development checklist.** Its principles can apply widely, but `project.json`, `flow.md`, pins, yarn, link pins, detail references, planned frames and AI post-its only make sense to a Sketchcoded consumer.

Recommended arrangement:

1. Keep universal preferences in `BUILD_CHECKLIST.md`: respect the user's design and wording, preserve intended behavior, surface ambiguity, retain deliberate decisions and unimplemented work, readable layouts, zoom, scrolling cues, targets, verification and process.
2. Keep the exact board format and navigation interpretation in `docs/skills/read-a-board.md`, `connect-screens.md` and the graph contract. These skills already ship in exports and are served to agents, so moving the rules does not lose them.
3. Keep Sketchcoded's own product choices in `SKETCHCODED_REQUESTS.md` and its board. Update references and mark transferred checklist entries as superseded rather than simply deleting history.

The copy rule should also express its general form (“Use the user's wording unless asked to rephrase”); its sentence about pin names belongs with board-reading instructions. Instructions about export filenames and the localhost checklist endpoint belong in agent-handoff documentation.

**Keep, but clarify scope rather than silently removing:**

- “Nothing grows or shrinks” should remain a rule against unintended layout shifts. The user separately requested intentional frame shrinking during category filtering and a small neighbor offset during selection; record those as explicit Sketchcoded exceptions.
- “The page never scrolls; panels do” was explicitly made general by the user. It is appropriate for the workspace, but the public guide is currently a scrolling reading page. Clarify whether reading/marketing pages are an intended exception; do not assume permission to weaken the rule.
- “Mobile is a stacked version” is an explicit user preference, not something to remove just because it came from this project. Its drawing-specific phrasing can live in the board-reading skill.
- The planned-frame “do not build” instruction needs its AI-frame exception in the same sentence. The checklist and short build-rules skill otherwise appear to prohibit the standard pages they subsequently require.
- “Never invent a route that is not drawn” should say “not authored”: provisional pins and yarn intentionally exist before any drawing.

## What I would cut, and what I would retain

Cut or replace misleading current instructions and dead placeholder links. Hide “See more projects” until it has a real destination, or point it to the user's chosen destination. Retire obsolete dashed-thread, filter and side-by-side instructions from the active spec while retaining their history. Simplify the overlapping documentation by assigning clear roles to the user guide, shared preferences, board-reading skills and project history.

I would not cut the outline, Plan, review, provisional pins, standard pages, export or watched-folder option: each serves a distinct agreed need. I would not restore the agent chat stub, invent substitute example drawings, or build extra external-site frames to make missing links look complete. The built-in Little chat sample remains useful for demonstrating branches and history; it should stay clearly separate from the public example made from the user's drawings.

## Implemented follow-up · 2026-09-28

The user authorized the follow-up and clarified that the full checklist is verified by the acting agent at both stages: board authoring (including delegated pages) and constructing the site. The earlier findings above are the review record, not a list of still-open defects.

- R1/R2: route changes await pending saves; failure keeps recovery controls available. Incoming refreshes recheck for local edits after the request. Regression tests exercise both lost-edit cases.
- R3: short windows use compact toolbars. At 1280×720 and real 250% tab zoom, the board now has **184 CSS pixels** of height (formerly 22.8), with reachable controls and no document scrolling. At 200% it has 256 pixels; at 150%, 376. At 1440×900 the respective 250/200/150/125% heights are 256/346/394.7/495.2.
- R4/R5: AI pages receive reachability and exit checks. Stored high-water counters prevent code reuse after deletion, undo or older-client saves.
- R6: the public demo handles external links, local/content pins, delegated pages, mobile positions, detail views, authored history and independent test rewind. Pan is clamped and walk targets are 44px. The site and guide use visible scrolling panels.
- R7: Content / local action pins preserve intentions that stay on the same screen without invented navigation. Their yarn is a structural error, and they never count as exits.
- The six-panel tutorial is implemented on the app landing page. The guide, README, functionality record and board backlog are current. The project link points to sciencewithagents.com. Board-specific checklist material was moved with its history preserved.

New acceptance checks exercise all six tutorial panels, fixed dialog sizing, board room, controls and AI page overflow at actual 125%, 150%, 200% and 250% tab zoom at 1440×900 and 1280×720. Existing browser tests cover editors, Review flow, mobile layout, branches, saved decisions and recovery. Public-site checks cover the same eight zoom combinations, live-board links and Guide rendering, plus fixture tests of nested modal/replace/dismiss, Back, reset, detail, rewind and sparse-board pan clamping. Browser screenshots were inspected as well as measurements.

This does not claim the undrawn frames are finished designs or that prototype forms have a backend. Embedded model execution and production code generation remain deliberately deferred. The full checklist is now an explicit instruction and completion requirement for the outside agent, not an automatically certified badge.

A final visual pass additionally caught oversized generated form/dialog/ending pages escaping their preview viewport and scroll hints covering dialog headings. Generated pages now stay inside their stage and scroll internally with a dedicated hint strip. Test flow uses compact chrome in short windows; notices and unplaced mobile pins stay in the scrolling sidebar so clicking a pin cannot shrink the drawing. The acceptance test checks both minimum working room and maximum page bounds, plus visible overflow hints.

Final gates: build, 102 unit/API tests, all 32 browser tests and formatting passed. The deployed homepage, guide, project link and generated Guide page were verified. The board zoom result is shown in [the follow-up screenshot](screenshots/review-2026-09-28-zoom-fixed.png).
